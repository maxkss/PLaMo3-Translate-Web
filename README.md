# PLaMo Translate (On-device) — Chrome 확장

[PLaMo 3 Translate](https://huggingface.co/pfnet/plamo-3-translate-2b) **0.8B / 2B**를 **브라우저 안에서 WebGPU로 직접 실행**하는 크롬 확장입니다. 서버로 텍스트를 보내지 않습니다.

- **드래그 번역**: 텍스트를 선택하면 번역 버튼이 뜨고, 누르면 스트리밍으로 번역합니다(우클릭 메뉴, `Alt+T`도 지원).
- **전체 페이지 번역**: 팝업의 "이 페이지 번역" 또는 `Alt+Shift+T`. 스크롤하지 않아도 페이지 전체를 번역합니다. 화면에 보이는 본문부터 시작해 화면에서 가까운 순서로 진행하고(스크롤하면 순서를 다시 정함), 문단은 번역이 끝난 뒤 한 번에 바뀝니다(글자가 하나씩 흘러나오지 않음). 바뀔 때는 원문이 옅고 살짝 흐려진 순간에 번역으로 바뀐 뒤 다시 선명해지고(약 0.5초), `원문 + 번역`에서는 번역 줄이 높이를 천천히 늘리며 나타나 아래 내용이 튀지 않습니다. 같은 순간에 끝난 문단은 위에서부터 차례로 바뀌며, 운영체제의 "동작 줄이기" 설정을 켜면 생략합니다. 동적으로 추가되는 내용과 SPA의 화면 전환도 이어서 번역합니다.
  - 표시 방식: `원문 + 번역`(기본) / `번역만`. "원문 보기"로 언제든 원래 페이지 그대로 복원합니다.
  - 링크·굵게·기울임·인라인 코드·각주 번호 등 문단 안의 서식을 유지합니다. 모델에는 `<a1>링크</a1>`, `<b2>굵게</b2>`, `<x3/>`(각주·이미지) 같은 번호 태그로 보내고, 번역문을 페이지의 **원래 텍스트 노드와 요소**에 다시 넣습니다(어순이 바뀌면 요소 순서도 바꿈). 페이지의 노드를 떼어내지 않아 React 같은 프레임워크가 계속 동작합니다.
  - 숨겨진 글자(`display:none`, 스크린리더 전용 텍스트)는 문단 번역에 섞지 않아, 번역이 사라지거나 안 보이던 글자가 나타나지 않습니다.
  - 코드 블록, 입력창, `translate="no"`, 이미 목표 언어인 문단은 건너뜁니다.
  - 짧은 형제 요소(같은 부모의 목록 항목, 표의 한 행, 메뉴 링크, 반복되는 카드 등 120자 이하)는 최대 16개·500자까지 한 줄씩 이어 한 번에 번역하고 줄 단위로 다시 나눕니다. 형제가 서로 문맥이 되어 짧은 메뉴의 오역이 줄고("Terms" → 약관, "Vulkan" → Vulkan), 줄 수가 맞지 않으면 각각 따로 다시 번역합니다.
  - 부모가 다른 반복 구조(행마다 있는 기사 제목, 카드마다 있는 가격)도 묶습니다. 위로 6단계 안에서 같은 태그·클래스의 형제가 3개 이상인 조상을 반복 항목으로 보고, 그 안에서 같은 경로에 있는 요소끼리(제목은 제목끼리) 묶습니다. 형제 묶음과 반복 묶음 중 대기 중인 요소가 많은 쪽을 씁니다. 실제 페이지 5곳에서 요청 수가 40–77% 줄었고(GitHub 417 → 95, Yahoo! JAPAN 326 → 81, Hacker News 72 → 38) 완료 시간은 같습니다.
- **이미지 번역**: 이미지에서 우클릭 → "PLaMo로 이미지 번역". 이미지 속 글자를 찾아 읽고(OCR) 문단마다 번역한 뒤, 원래 글자를 지우고 그 자리에 번역문을 씁니다(글자색·크기·정렬·세로쓰기를 원본에 맞춤). 모든 문단의 번역과 배경 복원이 끝난 뒤 한 번에 바꿔 보여 줍니다. 문단을 누르면 그 부분만 원문을 보여 주고, 오른쪽 위 아이콘에서 전체 원문 보기·지우기를 할 수 있습니다. 같은 메뉴를 다시 누르면 원래대로 돌아갑니다.
  - OCR은 [PP-OCRv5](https://github.com/PaddlePaddle/PaddleOCR)(Apache-2.0) 공식 ONNX 변환본을 처음 쓸 때 한 번 내려받습니다. 기본은 가벼운 구성(검출 mobile 4.8 MB + 인식 mobile 16.5 MB)이고, 설정에서 정확한 구성(인식 server 84.5 MB)을 고를 수 있습니다. 고정된 커밋에서 받고 SHA-256을 확인합니다(`OCR_MODELS`). 일본어·중국어·영어(라틴 문자)를 읽습니다.
  - OCR은 번역 엔진과 별도인 Worker(`ocr-worker.js`)에서 WebGPU로 돌아갑니다. 처음 모델을 불러오고 나면 이미지당 약 0.1–0.2초입니다(Apple M5). 1분 동안 이미지 번역이 없으면 OCR·배경 복원 모델을 메모리에서 내립니다.
  - 다른 사이트의 이미지도 확장 권한으로 직접 받습니다. 받을 수 없는 이미지(blob:, SVG 등)는 페이지에서 읽고, 그것도 안 되면 화면에 보이는 부분을 캡처해서 읽습니다.
  - 원문 지우기(`src/ocr/erase.ts`): 박스로 덮지 않고 글자 획 픽셀만 골라(글자색·배경색 기준, 테두리 번짐 포함) 지운 뒤 주변 배경으로 채웁니다. 단색·그라데이션 배경은 확산 채우기(이미지 피라미드)로 바로 처리하고, 사진·무늬 위 글자는 모바일용 인페인팅 모델 [MI-GAN](https://github.com/Picsart-AI-Research/MI-GAN)(Picsart, MIT)으로 복원합니다. 28 MB이고, 같은 영역에서 LaMa보다 약 4배 빠르며 메모리도 훨씬 적게 씁니다. 사진 위 글자가 처음 나올 때 한 번 내려받습니다. 글자가 작은 그림을 거의 다 덮어 복원할 바탕이 없으면 반투명 흐림 박스로 대신합니다. 번역문이 원문보다 길어 넓어지는 부분은 원래 배경 위에 그대로 씁니다. 기울어진 글자는 처리하지 않아(가로·세로 직사각형만) 사진 위 기울어진 글자는 일부 획이 남을 수 있습니다.
  - 앱 화면처럼 복잡한 이미지: 글자색·배경색이 다른 줄(이름과 미리보기, 로고와 가게 이름, 탭)은 다른 문단으로 나눕니다. 한 글자짜리나 아이콘을 글자로 잘못 읽은 것(돋보기 → "Q")은 건너뛰고, 번역해도 그대로인 글자("DISCOVER", "88VIP", 날짜)는 원본을 그대로 둡니다. 한 줄짜리 라벨은 줄바꿈하지 않고, 옆 배경이 비어 있는 만큼 박스를 넓힌 뒤 필요하면 글자를 줄입니다. 사진·그라데이션 위의 글자는 단색 박스 대신 반투명 흐림 박스로 덮습니다.
  - 원본과 같은 글자 크기·정렬 유지(`src/content/layout.ts`, `image-view.ts`):
    - 글자 크기는 검출 박스가 아니라 글자 잉크의 실제 높이로 잽니다(박스 여백은 박스 모양에 따라 달라짐). 번역문은 목표 언어 글자의 잉크 높이가 원문과 같아지도록 크기를 정합니다.
    - 방향·굵기가 같고 크기 차이가 12% 이내인 글자는 같은 "스타일"로 묶어 같은 크기를 씁니다(큰 제목→작은 제목→본문이 연쇄로 묶이지 않게 묶음 안 최대/최소 비율로 제한). 사진·아이콘 위 글자는 따로 둡니다.
    - 정렬(왼쪽·가운데·오른쪽)은 문단 안 줄들(들여쓰기·양쪽 정렬 고려), 가까이 이어진 위아래 글자 두 개 이상, 일정 간격으로 반복되는 행(아이콘 라벨 그리드·탭), 버튼·칩처럼 감싸인 글자에서 근거를 찾고, 근거가 없으면 왼쪽입니다. 번역문은 그 기준선에, 같은 행 글자는 같은 중심선에 붙입니다. 멀리 떨어진 카드·단끼리는 서로 영향을 주지 않습니다.
    - 같은 행·목록의 같은 스타일은 함께 줄어듭니다(구성원이 닿을 수 있는 크기의 하위 20% 값, 단 85% 아래로는 대부분이 그만큼 줄어야 할 때만). 한 줄 라벨은 옆 빈 공간(이미지에서 잼, 이웃 글자와는 0.6em 띄우고 절반씩)만큼 넓힌 뒤 줄입니다. 행·목록의 줄 수는 바꾸지 않고, 혼자 떨어진 문단만 아래 다음 글자 전까지 공간이 있으면 두 줄로 씁니다.
    - 굵기는 획 두께(면적·둘레 비율)를 크기에 맞춰 보정해 판단하고, 매끈한 그라데이션 배경은 같은 그라데이션으로 덮습니다.
- 53개 언어 지원(모델 기준). 기본 목표 언어는 한국어입니다.

| 모델 | 크기 | 디코딩 (Apple M5, Chrome WebGPU) | 변환본 |
|---|---|---|---|
| 0.8B (기본) | 0.50 GB | 약 175 tok/s | [chiro0318/plamo-3-translate-0.8b-onnx-webgpu](https://huggingface.co/chiro0318/plamo-3-translate-0.8b-onnx-webgpu) |
| 2B | 1.62 GB | 약 61 tok/s | [chiro0318/plamo-3-translate-2b-onnx-webgpu](https://huggingface.co/chiro0318/plamo-3-translate-2b-onnx-webgpu) |

모델 로딩 1–2초, 짧은 문장의 첫 글자 0.03초(0.8B)·0.1초(2B) 안팎.

## 구성

```
tools/convert/     PLaMo 3 → ONNX 변환 파이프라인 (Python, uv). 0.8B·2B 공통
  plamo3_onnx.py     원본 modeling_plamo.py와 수치가 같은 재구현 (검증: verify_torch.py)
  build_fused.py     ORT 융합 연산(GroupQueryAttention+RoPE, SimplifiedLayerNormalization)으로 그래프 직접 구성
                     (고정 크기 KV 캐시 입력, 마지막 층은 마지막 위치만 계산; 실험용 변형 옵션 포함)
  verify_variants.py 그래프끼리 greedy 출력이 토큰 단위로 같은지 CPU에서 비교
  quantize.py        4-bit 가중치 양자화(MatMulNBits / GatherBlockQuantized) → q4f16
  build_tokenizer.py 토크나이저 자산 + 기준 테스트 벡터 생성
  convert.sh         위 단계를 한 번에 실행 (convert.sh 0.8b | 2b)
tools/publish/     변환본을 Hugging Face에 올리는 스크립트 (hf CLI)
extension/         크롬 확장 (MV3, TypeScript, esbuild)
  src/engine/        토크나이저(원본 Viterbi 포팅), 생성 루프, 번역기, OPFS 모델 저장소, 추론 워커
  src/offscreen.ts   번역 서비스(작업 큐) — 모델은 전용 Worker에서 onnxruntime-web(WebGPU)으로 실행
  src/content/       드래그 번역 UI(Shadow DOM), 전체 페이지 번역, 이미지 번역 오버레이(image.ts)
  src/ocr/           이미지 번역용 OCR(PP-OCRv5): 검출·인식 전후처리, 문단 묶기, 색 추출(ocr.ts), 전용 Worker
  src/pages/         팝업, 설정(모델 설치·테스트) 페이지
```

## 사용 방법

### 1. 확장 빌드

```bash
cd extension && npm install && npm run build
```

### 2. 크롬에 설치

`chrome://extensions` → 개발자 모드 켜기 → **압축해제된 확장 프로그램을 로드합니다** → `extension/dist` 선택.

### 3. 모델 설치

확장 설정 페이지(팝업의 "모델 설정 · 테스트")에서 0.8B 또는 2B를 고르고 **내려받기**를 누릅니다.

- Hugging Face의 변환본을 **고정된 커밋**에서 받고, 파일마다 크기와 SHA-256을 확인합니다(`extension/src/shared/common.ts`의 `MODELS`).
- 중간에 끊기거나 취소해도 다시 누르면 받은 부분부터 이어받습니다(HTTP Range).
- 두 모델을 모두 설치해 두고 언제든 바꿀 수 있습니다. 바꾸면 다음 번역부터 새 모델을 불러옵니다.
- 모델은 확장의 OPFS(Origin Private File System)에 저장되어 이후에는 오프라인으로 동작합니다.
- 이전 버전에서 업데이트한 뒤 모델이 "설치되지 않음"으로 나오면 내려받기를 한 번 더 누르세요. 가중치는 같아서 작은 그래프 파일(0.1 MB)만 새로 받습니다.

고급 설정에서 다른 주소(예: `npm run serve-model`로 띄운 `http://localhost:8787/`)를 쓰거나, 직접 변환한 폴더를 가져올 수도 있습니다. 어느 경우든 체크섬이 맞아야 설치됩니다.

## 모델 변환 · 배포 (개발자용)

`uv`와 약 15GB 여유 공간이 필요합니다.

```bash
tools/convert/convert.sh 2b     # 또는 0.8b
```

결과물: `models/onnx/plamo-3-translate-<크기>/onnx/model_q4f16.onnx` + `model_q4f16.onnx_data`.

Hugging Face에 올리기 (`hf auth login` 필요):

```bash
tools/publish/publish.sh 2b
```

모델 카드(라이선스 메타데이터, "Built with PLaMo"), PLaMo Community License 사본(영/일), 원본 `config.json`, 파일별 SHA-256이 담긴 `manifest.json`을 함께 올립니다. 출력된 커밋 해시를 `MODELS[...].revision`에 넣으면 확장이 그 버전을 받습니다.

## 속도 최적화

단일 번역 지연을 줄이기 위해 다음을 적용했습니다. 모두 기존 그래프와 **출력 토큰이 같다**는 것을 확인한 것만 넣었습니다.

- **고정 크기 KV 캐시 + WebGPU 그래프 캡처**: KV 캐시를 2,048토큰짜리 GPU 버퍼에 두고 입력·출력으로 같은 버퍼를 넘깁니다. 한 토큰씩 생성하는 단계는 캡처해 둔 그래프를 재생하고, 프롬프트 처리는 캡처 없이 실행합니다.
  - onnxruntime-web 1.31은 이 조합을 그대로 지원하지 않아 `extension/build.mjs`에서 JS 연결 코드 두 곳을 빌드할 때 고칩니다(버퍼 등록 유지, 강제 재바인딩). 표시가 없는 버퍼는 동작이 같습니다.
- **GPU argmax**: logits를 GPU에 둔 채 작은 WGSL 커널로 다음 토큰을 고르고 4바이트만 읽습니다. (ONNX ArgMax는 오히려 느렸습니다.)
- **마지막 층 조기 슬라이스**: 마지막 층의 어텐션 뒤로는 마지막 위치만 계산합니다(프롬프트 처리 약 4% 단축).
- **프롬프트 앞부분 KV 재사용**: 직전 요청과 같은 토큰으로 시작하면 그 부분은 다시 계산하지 않습니다. 프롬프트 처리 비용이 32토큰 단위로 올라가서, 경계를 넘던 프롬프트는 2B에서 약 50 ms 빨라집니다.
- **배치 디코딩 (최대 3개)**: 페이지의 여러 블록(긴 글의 여러 조각 포함)을 한 번에 최대 3개씩 같이 생성합니다. 각 블록의 프롬프트는 따로 처리해 KV를 배치 버퍼의 한 줄로 복사하고, 그 뒤로는 줄마다 길이가 다른 채로 함께 한 토큰씩 생성하며, 끝난 줄은 바로 다음 블록으로 채웁니다. 3개까지는 혼자 번역할 때와 **출력 토큰이 같은 것**을 확인했습니다(2B·0.8B 각 12문장 12/12). 4개 이상은 다른 커널이 선택돼 일부 문장의 표현이 달라질 수 있어 쓰지 않습니다.
  - 그래프의 배치 차원을 가변(`batch`)으로 바꿨습니다. 가중치 파일은 그대로이고 0.1 MB짜리 그래프 파일만 바뀝니다. 한 문장만 번역할 때 속도는 이전 그래프와 같습니다(디코딩 +1~1.5%, 프롬프트 처리 동일).
  - 배치 그래프가 아니면(이전 그래프, wasm) 예전처럼 한 번에 하나씩 처리합니다.
- **선택 번역 우선 처리**: 페이지 번역 중에 드래그 번역을 요청하면 배치 중인 블록은 KV를 유지한 채 잠시 멈추고, 선택 번역을 혼자(캡처된 그래프로) 먼저 처리합니다. 배치를 쓸 수 없을 때는 진행 중인 문단을 멈추고 다시 큐에 넣습니다.
- **스트리밍**: 첫 글자는 바로 보내고 이후에는 40 ms 간격으로 묶어 보냅니다.
- **페이지 번역**: 화면 밖 블록도 모두 번역하고(화면 → 가까운 순), 끝난 문단을 다음 프레임에 함께 그립니다(아래 벤치 수치는 스트리밍으로 그리던 때 측정). 같은 내용의 요청이 동시에 들어오면 한 번만 계산해 결과를 나눠 줍니다.
  - Sakutto 벤치 페이지(2B, 스크롤 없음), 처음 → 전체 번역·스트리밍 → 배치 추가:
    - many-cards 전체 33.1 → 22.0 → 16.5초, 첫 화면 22.4 → 14.8 → 12.0초
    - long-article: 끝나지 않음 → 51.3 → 36.6초
    - 긴 문단 하나(374토큰, 한 조각): 첫 글자 24.2 → 1.2 → 0.8초, 완료 약 20초. 한 조각이라 배치 효과가 없습니다.
  - 배치 때문에 맨 위 문단 하나만 보면 완료가 조금 늦어집니다(long-article 2.1 → 3.2초). 다른 블록과 GPU를 나눠 쓰기 때문이며, 첫 글자는 더 빨리(0.85 → 0.33초) 나타납니다.

실측(이전 대비, 같은 문장 5개): 0.8B 전체 시간 −16%(디코딩 148→176 tok/s), 2B −8%(57→61 tok/s), 첫 글자 −18%.

측정에 쓴 도구(`BENCH=1 npm run build`로만 포함):
- `extension/src/dev/bench-ab.ts`: 두 그래프를 한 페이지에 올려 번갈아 측정하는 A/B, 출력 토큰 비교 포함
- `extension/src/dev/bench-engine.ts`: 같은 문장들을 하나씩 / 동시에(배치) 생성해 토큰이 같은지와 시간을 비교, 배치 중 선택 번역 지연 측정
- `extension/test/bench.mjs`, `extension/test/ab.sh`: 위 벤치 페이지 실행

효과가 없거나 손해여서 버린 방안: 0.8B 초안 추측 디코딩, ONNX ArgMax, SkipSimplifiedLayerNorm·QuickGelu 수동 융합(출력이 달라짐), q/k/v·gate/up 분리로 ORT 내장 융합 유도, 양자화 블록 64/128(프롬프트 처리가 4.4배 느려짐), JSPI 빌드, validationMode, 디스패치 묶음 크기.

## 알려진 제약

- 한 번에 처리하는 문맥은 2,048 토큰(슬라이딩 윈도 범위)으로 제한하고, 긴 글은 문단·문장 단위로 나눠 번역합니다.
- WebGPU가 없으면 WebAssembly(CPU)로 대체되지만 fp16 모델이라 매우 느립니다.
- 모델이 서식 태그를 빠뜨리면(0.8B에서 위키백과 링크 971개 중 1개 정도) 그 부분은 링크 없이 글자만 남습니다. 닫는 태그만 빠진 경우는 다음 구두점까지를 링크로 복구합니다.
- Shadow DOM 안의 글자(웹 컴포넌트 내부)는 번역하지 않습니다.
